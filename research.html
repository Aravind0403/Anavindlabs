Clairvoyant: Predictive Request Scheduler for LLM Serving

Preprint: arXiv:2606.07248 · Stack Layer: Request Scheduling (L1)

Standard LLM serving proxies process incoming requests under First-Come-First-Served (FCFS), leading to head-of-line blocking when high-token generations stall short conversational queries. Clairvoyant is a backend-agnostic Go sidecar proxy that intercepts incoming HTTP/gRPC requests before GPU engines (Ollama, llama.cpp) with zero modification to upstream code. It evaluates a 19-feature XGBoost classifier exported to ONNX to infer generated token length in 0.029ms P99 (approximately 70,000× faster than generation time) and re-orders dispatch using Shortest-Job-First (SJF).

Critical Engineering Finding & Disconfirmed Result

Curated synthetic instruction datasets (Alpaca-style) are unusable for length-predictor training. Models trained on Alpaca exhibited severe prediction collapse because GPT-generated responses suffer from artificial brevity bias. The classifier learned to rank based on synthetic instruction patterns rather than natural token distribution. True predictive ranking required training on uncurated multi-turn human conversation logs (ShareGPT and LMSYS-Chat-1M).

Kube-Sentinel: Native Kubernetes GPU Scheduler Plugin (V2)

github.com/Aravind0403/Kube-Sentinel · Stack Layer: Cluster / GPU Scheduling (L2)

Kube-Sentinel is an enterprise-grade, high-throughput Kubernetes custom scheduler designed for heterogeneous cloud and GPU clusters. It decouples high-speed scheduling execution (a native Go plugin implementing the Kubernetes Scheduling Framework) from mathematical telemetry verification (a Python daemon communicating over a sub-millisecond loopback gRPC channel).

Core Distinction: Measured Latency vs. Modeled Savings

The 1,252.6 pods/sec scheduling rate and sub-millisecond P99 latency were empirically measured on live GKE Kubernetes nodes. In contrast, the 46.3% GPU dollar savings is an offline simulation result derived from replaying Alibaba's 2018 cluster traces. I do not present this simulation as a verified production financial saving.

Aether Control: vLLM Control Plane & GRPO Post-Training

github.com/Aravind0403/aether-control-llm-infra · Stack Layer: Serving Control Plane & Training Guards (L3 / L5)

Aether Control is a resilient production control plane for vLLM serving and critic-free GRPO (Group Relative Policy Optimization) post-training under DeepSpeed ZeRO-3. It integrates four tightly coupled architectural mechanisms: (1) Controlled Delay (CoDel) load shedding to drop requests when queue latency exceeds a strict 500ms target; (2) Radix-cache tenant quotas to prevent memory hogging; (3) Ingress consistent-hash routing to preserve multi-pod prefix-cache locality (>95% hit rate); and (4) Chunked prefill scheduling to eliminate head-of-line blocking under long-context prompts.

Root-Causing the 81–93% Throughput Collapse

During initial stress testing under an aggressive VRAM target, the cluster suffered an abrupt 81% to 93% throughput collapse. Standard debugging would suggest reducing the VRAM target. Instead, heap profiling revealed the root cause: ungated high-variance sequence lengths caused catastrophic batch padding waste and sudden page thrashing in vLLM's memory allocator. Rather than surrendering GPU efficiency, I built TrainSight — a sub-millisecond CPU-based pre-flight InitContainer profiler that flags variance and OOM risk before admission, achieving F1=1.0000 across test sets, increasing batch throughput by 81.0%, and cutting padding waste by 40.2%.

HeteroDisagg: Hardware-Aware Disaggregated Serving

github.com/Aravind0403/HeteroDisagg · Stack Layer: Cross-Hardware Serving (L4)

Existing serving engines (vLLM, SGLang) assume homogeneous GPU clusters. In contrast, HeteroDisagg disaggregates prefill and decode across mismatched GPUs. A dynamic Roofline Profiler measures real compute TFLOPS and memory bandwidth on each device, mapping high-TFLOPS GPUs (e.g. A100) to prefill and high-bandwidth-per-dollar GPUs (e.g. RTX 3090) to decode. To bridge mismatched tensor-parallel degrees (e.g. TP=4 prefill to TP=1 decode), I designed HeteroKVConnector, which reshardens KV-cache blocks in flight while applying block-wise FP8 quantization.

Featured Disconfirmed Result: Kernel Overhead vs Wire Savings

On-device profiling revealed an unmistakable negative result: the isolated CUDA quantization and layout transformation kernel is slower than transmitting raw FP16 due to thread divergence and block reduction overhead (+11ms to +32ms depending on batch size). The architecture is a net win only under network-constrained cross-node interconnects (e.g., PCIe / 10GbE / commodity cloud links) where cutting byte transfer by 50% amortizes the kernel cost. Any production claims regarding high-speed fabrics (NVLink/RoCE) remain analytical projections and are not claimed as measured wins.

ServiceScope: Pre-Deployment Blast-Radius Prediction

github.com/Aravind0403/ServiceScope-v2 · Status: Draft paper exists (Not submitted / Not accepted)

A static pre-deployment blast-radius analyzer for distributed microservices. Combines Tree-sitter polyglot AST parsing across 5 programming languages with a deterministic cross-layer manifest linker (Kubernetes manifests, Helm templates, Docker Compose). Confirmed F1=1.000 accuracy on Google's microservices-demo and OpenTelemetry's opentelemetry-demo, executing in a sub-500ms CI stage with <50ms manifest resolution.
